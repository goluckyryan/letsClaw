Everything in this file is read from config.yaml (gitignored — it holds API keys and the bot token). Copy config.example.yaml to start. Most settings are picked up live by /reload (or the ♻️ button in the WebUI) with no restart and no dropped socket; the exceptions are core.bind, core.port and logging.file — the socket is already bound, and rebinding it would drop every client. The live / restart column below says which is which for each setting. A setting a session changed for itself is left alone on reload.

behavior

The Markdown sent with every prompt, in three layers: a shared base file, a per-model file, and an optional per-session file. A missing file is a warning at startup and an empty layer — the core keeps running.

keytypedefaultreloadwhat it does
base_filepathmodels/base.md live The layer shared by every model — identity, working style, tool notes. Read on every prompt rebuild.
session_dirpathunset live The third layer: <session_dir>/<session name>.md, injected after the model file and before any rollover handoff. Keyed on the session name, which is what makes it per-channel for Discord without the core knowing Discord exists — the bot names sessions after channels, so models/sessions/dudus-den-solaris.md is that channel's file. Same for the terminal (terminal.md) and any WebUI session. Unset = the layer is off. Creating a file for an already-live session needs a /reload to be noticed, the same as editing base.md.

models

A registry of named models. Every entry is self-contained — it names its own server, so reading one entry tells you everything about that model. Two models can live on two different servers with different window sizes. default_model picks the model a new session starts on; /model <name> switches one session at runtime without disturbing the others. -m <name> on the terminal client overrides at startup.

keytypedefaultreloadwhat it does
default_modelname— liveWhich entry a new session starts on.
<name>.*entry— liveOne model. The keys below are per entry; base_url is the only required one.
  provider_namestringthe key liveThe exact model ID the server reports — check /v1/models. Falls back to the entry key.
  base_urlurlrequired liveThe OpenAI-compatible endpoint serving this model. A missing one is caught when the engine is built.
  api_keystring"" liveOmit or "" when the server needs no key.
  behavior_filepathmodels/default.md liveThe per-model layer, on top of behavior.base_file. Each model can have its own.
  context_lengthint12000 liveTotal window the server was launched with — the budget the ⚡ stats line reports against (max_tokens caps output only). Worth getting right rather than guessing low: it also sets the pre-turn thinking-headroom check, so a value under the server's real window rolls sessions over early. llama.cpp reports the per-slot figure at GET /props as default_generation_settings.n_ctx.
  temperaturefloatserver default liveSampling temperature. Omit to leave the server's default.
  top_pfloatserver default liveNucleus sampling. Omit to leave the server's default.
  max_tokensintserver default liveOn a thinking model this caps reasoning and the answer together — really "how much the model may generate per round," a chunk size, not a limit on total thinking. A round cut off mid-reasoning is resumed, not re-asked (see README, Reasoning). Smaller is not cheaper: the pad is re-sent every round, so halving this roughly quadruples the prompt tokens processed for the same thinking.
  max_output_tokensint32768 liveThe answer sheet. Once thinking is closed with </think>, the closing round runs under this cap and every token of it buys answer, not reasoning. 0 = the closing round keeps max_tokens.
  reasoningbooltrue liveWhether a cut-off round is resumed at all. There is deliberately no budget on how many times it may resume: the pad grows until time or context stops it, or until a round comes back having written nothing. false = no pad: a cut-off round falls back to the base.md directive.
  strip_directivesboolfalse liveKeep the "## Checkpoint" and "## Forced conclusion" blocks out of the system prompt for this model. They are templates the core sends as user messages when each applies; they sit in base.md only so they can be tuned. A local thinking model ignores the copy in its prompt, but a hosted assistant reads the whole prompt as standing instruction and obeys it — set true for a hosted API, leave false for local models.
  turn_timeoutsec36000 liveHard wall for one turn, in seconds — a limit on a round, thinking model or not. It also sets the HTTP client's read timeout, so a round that runs longer is cut off and the turn cancelled (the conversation is saved). 0 = no wall. Default is 10 h.
  answer_time_reservesec120 liveSeconds held back from turn_timeout so the answer still fits inside the wall after a long think. Thinking stops at turn_timeout − answer_time_reserve.
  max_pad_compactionsint0 liveWhen the pad fills the context, distil it to a checkpoint (the model's own note of what it has established) plus the last ~2000 tokens kept verbatim, then carry on thinking. This is the only wall that can be pushed back, so it is what makes thinking bounded by time rather than by context. 0 (default) = never compact: fill the context and conclude. Compaction is lossy — raise this only for analyses long enough that running out of room is the worse outcome. The note comes from "## Checkpoint" in the base file.
  resume_modeenumauto liveHow a cut-off round is resumed: auto = probe the server once and pick (default); chat = OpenAI-compatible prefill (vLLM/SGLang continue_final_message); raw = llama.cpp /apply-template + /completion; off = no resume, fall back to the base.md directive, losing the work.
  reasoning_effortstringserver default livePassed to the chat template. Qwen3 turns this into a system directive; llama.cpp defaults to xhigh, which on its own causes a lot of the mid-reasoning cut-offs — medium adds no directive at all. Omit to leave the server's default alone.
  ssh_forwardtargetunset liveReach this model through a port-forward the core owns (the server is behind a jump host). The value is the destination as ssh takes it (user@ip / ip / alias). The core spawns ssh -N -L 127.0.0.1:<port>:127.0.0.1:<remote> itself and points the engine at it. base_url is then a placeholder port. See core.ssh_health_sec.
  ssh_jumptargetunset liveThe jump host to reach ssh_forward through, as a ProxyCommand (not -J, which drops options on the inner hop). Keeps the whole path in config so it works on a fresh machine with only the ssh keys.
  ssh_remote_portintunset liveThe port on the ssh_forward destination — always its own loopback, so just the port. Legacy ssh_remote: host:port is still read, host ignored.

core

The service itself. Start it first (./serve.sh); clients connect to it. --bind / --port / --config on ./serve.sh override the first three at startup.

keytypedefaultreloadwhat it does
bindaddr127.0.0.1 restartInterface to listen on. Loopback by default — tools are unconfined, so anyone who can reach this port gets a shell here. Keep it on loopback or set token.
portint8770 restartThe WebSocket port; the WebUI is served on the same one at http://<bind>:<port>/.
tokenstring"" liveOptional shared secret; required in practice if bind is not loopback. Every route needs it as Authorization: Bearer <token> or ?token= — except GET /health (stays open for monitors) and the WebUI itself (served unauthenticated; the page prompts for it and keeps it in localStorage).
allowed_hostslist[] liveExtra Host header values the core will answer to. Loopback, bind, this machine's hostname and FQDN and the addresses those resolve to are accepted already — add a name here only when something in front (a reverse proxy) forwards one the core has never heard of. Anything else gets a 403 before it routes; see the Security note below for why the check exists.
ssh_health_secsec30 liveHow often the keepalive checks the core-owned ssh port-forwards (models.*.ssh_forward) and respawns a dropped path on the same port. /models reports each forward; a missing pid means the path is down.
Security. Tools are unconfined by design: exec runs shell commands and read_file/write_file reach any path this process can. Anyone who can open a WebSocket to the core can run commands on this machine. Keep bind on loopback or set token, and only connect frontends you control. Loopback alone does not keep a web page out — a page you merely visit can reach 127.0.0.1 — so requests must also carry an Origin matching the Host, and a Host that names this machine. Both halves are needed: matching Origin and Host is also what a page gets when its own domain is re-pointed at 127.0.0.1, and only the second check, against names an attacker cannot add to (allowed_hosts), rejects that. Note what the Discord bot does to that last sentence — it bridges the core to anyone who can message the bot, so discord.users, not core.bind, is what stands between a stranger and a shell. See discord.

tools

The agent's tools. Unconfined by design — the allowlist and workdir are convenience, not a sandbox.

keytypedefaultreloadwhat it does
enabledboolfalse liveMaster switch for all tools. false (or the key absent) = the model gets no tools at all.
allowlistall four liveAllowlist: [exec, read_file, write_file, list_dir]. Anything not listed is denied with an error the model can read.
exec_timeoutsec120 liveSeconds before an exec command is killed.
max_output_charsint8000 liveTool output truncation — this is also the clip before output enters history.
workdirpathrepo root liveBase directory exec runs in and relative paths resolve against. Defaults to the letsClaw directory — the core is a daemon, so its own cwd is not the shell you started it in.

conversation

History, rollover and the journal. The context window itself is per model, under models.

keytypedefaultreloadwhat it does
max_history_messagesint100 liveBackstop: trims the oldest messages (never opening on an orphaned tool result) and only applies on turns where no rollover happened. Rollover is the real mechanism; this just stops an unbounded session with rollover switched off.
rollover_at_percent%90 livePercent of the model's context_length that trips a rollover. 0 = never.
rollover_modeenumauto liveauto = roll over and say so; ask = prompt [y/N] (and in Discord, post the question); off = warn only. /new forces a rollover in any mode.
rollover_before_thinkbooltrue liveRoll over before a turn with no context left to think in, rather than after one whose thinking was squeezed out. auto mode only; ask/off are never interrupted pre-turn.
prompt_timeoutsec60 liveSeconds to wait for a rollover answer (in ask mode) before keeping the session.
live_dirpathstate/live liveLive conversations, one JSON file each, reloaded when the core restarts. Written after every turn and on a clean stop; a kill -9 costs at most the turn in flight.
sessions_dirpathstate/sessions liveArchived transcripts and the journal segments beside them. Nothing expires — a session stays until deleted.
journalbooltrue liveThe Markdown record written as the turn runs, holding every round's reasoning and every tool call/result in full — none of which the JSON transcript can carry (reasoning never enters history; tool output is clipped to max_output_chars before it does). Lands in sessions_dir as <id>_<name>_<timestamp>.md, closed by a rollover, and the new window is told to grep it before repeating an investigation. This is what stops the model re-deriving what it already worked out one window ago. See The journal in the README.
journal_max_block_charsint1000000 liveCap on one recorded block, so a runaway cat costs a megabyte and not the volume. Nothing you would deliberately run comes close.

logging

The core logs here and to stderr. Every session event of consequence (restore, rename, delete, rollover, a dropped tool-call turn) is one line in it.

keytypedefaultreloadwhat it does
levelenumINFO liveDEBUG / INFO / WARNING / … . Model-call chatter (httpx) is pinned to WARNING so it does not drown the log.
filepathunset restartWhere the log is written. Restart-only, like core.bind/core.port. The writer's name is inserted before the suffix — the core writes letclaw-core.log and the Discord bot letclaw-discord.log, because they are two processes and one file for both would interleave their lines and rotate out from under each other.
max_bytesint10485760 restartSize at which the file rolls, in bytes (10 MB). Floored at 1 MB: anything smaller — including 0, which the rotating handler reads as never rotate, the exact opposite of what the key name promises — is refused with a warning on stderr and the default is used instead. A number that cannot be read is the default too.
backupsint5 restartHow many rolled copies to keep (letclaw-core.log.1 … .5). With max_bytes this is the whole ceiling: the logs occupy at most max_bytes × (backups + 1) per writer.

webui

Style of the pinned prompt (the newest user message, stuck to the top of the log while a turn runs) and the page theme. Served to the page as /theme.css; /reload re-themes every open tab with no restart (it rides the reloaded event — a browser will not re-fetch a stylesheet that is already loaded). Omit any key to keep the built-in default.

keytypedefaultreloadwhat it does
files_dirpathstate/files liveWhere the agent's pictures come from. An answer that writes ![a plot](run42.png) makes the WebUI fetch /files/run42.png, served from here and nowhere else: the path is confined to this directory (a traversal or a symlink out of it is refused) and must name an image extension, because this is the one route that turns model output into a filesystem read. Repo-relative unless absolute.
themeenumauto liveauto = follow the OS, dark, or light. A typo falls back to auto.
pin.backgroundcss colorvar(--bg) liveCSS color of the band behind the pinned message. var(--bg)/var(--fg) follow the page's light and dark themes; any literal works too ("#1e222b"). Only the bubble wears the inverted palette; the band follows the page.
pin.transparencyfloat1 live0 = fully see-through, 1 = opaque.
pin.font_sizecss lengthinherit liveThe pinned message's text size, e.g. "15px".
pin.font_colorcss colorvar(--fg) liveThe pinned message's text color.
A typo in a pin key is dropped, not forwarded — only the four known keys survive, so a misspelling cannot reach the page as a broken custom property.

discord

The Discord bot — a client like the terminal and the WebUI, in its own process. Only ever read by the bot; the core never imports discord.py and does not know it exists. Omit the whole section if you do not want a bot. ./serve.sh starts it alongside the core when enabled is not false and token is set; ./run_discord.sh starts one on its own, for a bot on another machine.

Read restart here as restart the bot, not the core — this section is the bot's own process, and the core never looks at it. Only the three access keys are live, and deliberately so: /reload has to be able to take someone's access away, because that person has an unconfined shell on this host until it does. The rest arrives on an event from the core, and re-pointing a running bot at another core or silently changing how it posts on the strength of one is not what a reload should do.

A bot is a remote shell. The tools are unconfined, so anyone who can get a message to this bot can run commands on the machine hosting the core. Anyone on Discord can DM a bot by default, and in a guild the only wall is Discord's own channel permissions. So users is a required allowlist of snowflake IDs, and an empty list refuses everybody — the safe default, not an oversight: fill it in deliberately. (Discord → Settings → Advanced → Developer Mode, then right-click a user → Copy User ID.)
keytypedefaultreloadwhat it does
enabledbooltrue restartThe off switch. false keeps the bot from starting and makes ./run_discord.sh refuse to run. Absent means enabled.
tokenstring— restartThe bot token (config.yaml is gitignored, so it stays put). Switch Message Content Intent on under Privileged Gateway Intents or every message arrives empty. Invite with the bot scope + Send Messages + Read Message History.
coreurlfrom core.* restartWhere the core is, ws://host:port. Defaults to what core.bind/core.port build.
core_tokenstringcore.token restartThe core's shared secret. Set only if the bot runs on another machine from the core.
userslistempty liveRequired allowlist of snowflake IDs. Empty = nobody gets through, including the owner — the startup default.
mention_onlyenumtrue liveMust the bot be addressed (@mention or a reply) before it answers in a guild channel? Hygiene, not security — it keeps the bot quiet in a busy channel. DMs always answer. true = always address it; false = it answers everything; white = address it only in the channels in mention_list; black = address it everywhere except those. An unreadable value falls back to true rather than opening the bot up. The bot prints the resolved answer for every channel at startup. With the rule off for a channel, a bare "yes" there can also answer a pending rollover question — reason enough to leave the busy ones on.
mention_listlistunset liveChannel names, #name, server/channel when two servers share a channel name, or raw snowflakes — matched as slugs, so #Ptolemy-Translation and ptolemy-translation are the same entry. A bare name matches that channel in every server. Ignored when mention_only is true or false.
idle_detach_minmin0 restart0 (the default) = never: the channel stays attached for the life of the bot, so a turn run from the WebUI still posts to Discord and there is no idle re-attach to get a session's name wrong. A number of minutes = the old behavior: the channel's socket is dropped when it goes idle that long and re-attached on the next message. The conversation is on the core either way, so nothing is lost; the link reconnects on its own with backoff and resumes by last_seq.
max_messagesint8 restartHow many messages one answer may become before the whole thing goes up as an answer.md attachment instead of flooding the channel. 0 = unlimited — always post in full, never file it. Safe: an answer is capped by the model's max_output_tokens (~65 messages at 32k, ~16 at 8k), and discord.py throttles itself on a 429. A busy shared channel is the reason to keep a limit; a private one is the reason not to.
max_linesint17 restartSoft cap per message; Discord collapses tall ones. Fences are closed and reopened so a code block never leaks into the next message.
auto_namesbooltrue restartName sessions after the server and channel — dudus-den-solaris — rather than the raw snowflake, so the WebUI sidebar reads like Discord does. The snowflake is still the key: the bot records the name it gave each channel id in state/discord_names.json, and when Discord's name changes it renames the core session instead of starting an empty one, so a renamed channel keeps its conversation (a WebUI rename is followed too — the channel is bound to the new name, so a reconnect never opens an empty twin). The server prefix is not decoration: two servers each with a #general is the normal case, and without it their conversations would silently merge into one session. false = bare discord-<channel_id>; DMs are always keyed on the user either way.
Pointing a channel elsewhere. /session <name> (or !session <name>) repoints the channel at any session — or creates it. The mapping is persisted in state/discord_session_map.json, survives a bot restart, and is left alone by the rename-following logic (user intent, not a name the bot chose). /session with no name shows the current binding; /session auto brings the channel back to its default name. Several channels can share one session; /info says which channel it is bound from.
