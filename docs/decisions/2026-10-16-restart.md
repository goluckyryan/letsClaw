# `/restart` — restarting the core from a client

**Shipped 2026-10-16** · supersedes `docs/restart_design.md`, which recorded the
same design on 2026-10-13 under the heading "nothing here is in the tree"

The [README's `/restart` section](../../README.md#restart--for-the-keys-reload-cannot-reach)
is the user-facing documentation and [protocol.md](../protocol.md) has the
command's place in the three groups. This is the record of why it is built the
way it is, and of four things that were nearly built wrong.

---

## Why

`/reload` re-reads `config.yaml` into a running core, but five keys cannot move
that way: `core.bind` and `core.port` (the socket is bound) and `logging.file`,
`logging.max_bytes`, `logging.backups` (read once when the handlers are
installed). The documented answer was "find a shell on the core's host and run
`systemctl --user restart letsClaw`", which is fine at the keyboard and useless
from the WebUI, a Discord channel, or a terminal client on another machine.

## The mechanism: same-PID `os.execv`

The core is a background child of `serve.sh`, which ends in `wait "$core_pid"`,
under a systemd unit whose `ExecStart` is `serve.sh` itself with
`Restart=on-failure`. `execv` replaces the image and keeps the PID, so the
`wait` keeps waiting and systemd never sees a service that stopped. Anything
that forked, or that exited and leaned on `Restart=on-failure` to come back,
would break both of those.

Three facts this rests on, each verified against the tree rather than assumed:

- log file descriptors are `FD_CLOEXEC` under the `RotatingFileHandler`, so they
  close on `execv` and reopen in the new image;
- no `set_inheritable`, `pass_fds` or `preexec_fn` anywhere, and PEP 446 makes
  new fds non-inheritable, so nothing leaks across;
- `runner.cleanup()` closes the listening socket before `run_app` returns, and
  `SO_REUSEADDR` is set by default on POSIX, so the new image can rebind.

## Four things that were nearly wrong

### 1. The obvious trigger is a signal, and a signal is ambiguous

The first design sent `os.kill(os.getpid(), SIGINT)`. aiohttp installs the same
`_raise_graceful_exit` for SIGINT *and* SIGTERM, and `serve.sh`'s own trap sends
`kill -INT "$core_pid"` — so `systemctl stop`, Ctrl-C and `/restart` all arrive
inside the process as one indistinguishable `GracefulExit`, and a stop landing
in the restart's grace window would bring back a core that was meant to die.
Nobody can correct that from the keyboard they just pressed Ctrl-C on.

So there is no self-signal. A `loop.call_later` callback raises
`web.GracefulExit()` directly — a `SystemExit` subclass, which `Handle._run`
re-raises rather than routing to the exception handler.

### 2. Two flags, because arming is not deciding

`armed` is set when `/restart` is accepted; `exec` is set only inside the firing
callback, and `main()` consults nothing else. An external stop during the grace
raises its own `GracefulExit` first, the timer never runs, `exec` is still
`False`, and the core stays down.

That was not enough on its own, and the gap only showed up under a real core: an
external stop does not *cancel* the pending timer, so the timer fired partway
through aiohttp's own cleanup and re-exec'd anyway. Two further defences, kept
together because they fail in different places:

- `_on_shutdown` cancels the timer before it awaits anything;
- a signal guard installed from `on_startup` — which `BaseRunner.setup()` runs
  *after* it adds aiohttp's own handlers, so ours replace them — records
  `stopping = True`, and the callback checks it. This covers a cancellation that
  takes longer than the grace to reach `_on_shutdown`, which the cancel alone
  does not.

A `systemctl stop` inside the grace window now exits 0 and stays stopped.

### 3. A restart onto a broken config is a restart loop, not a failed restart

`serve.sh` hands the core's exit status to a unit with `Restart=on-failure`,
`RestartSec=3` and **no `StartLimitBurst`**. A core that exits 1 on a config it
cannot parse therefore does not come back with a message — it disappears into a
loop. And `/restart` is exactly what someone reaches for *just after* editing
`config.yaml`.

So the config is validated before anything is armed: parsed, then run through
`config.boot_blockers()`, which holds the two refusals `main()` makes after the
file parses (a `core.port` that is not a port number, a non-loopback `bind` with
no `core.token`). `LOOPBACK` moved into `config.py` for this — `core.py` cannot
import `server.py`, and three copies of "what counts as loopback" would drift.

This refusal is deliberately **not** overridable by `force`. `force` is about
losing turns; nothing should talk you into a restart loop.

### 4. The reply has to beat the close frame

The WebUI's in-flight `rpc()` promise is rejected when the socket closes, so a
restart that closed first would render a success as an error. The command reply
is unicast inline from `ws_handler`, before the grace timer fires, so it needs
no grace at all. The *broadcast* notice does: it goes through the per-socket
`_writer`, and `_on_shutdown` drains the queues (bounded by `DRAIN_GRACE`)
before closing — a real postcondition rather than a guess at how long a flush
takes.

## The scope decisions

- **Refuse while a turn is running**, naming every busy session, with
  `/restart force` as the override. `Session.close()` cancels turns now, so this
  is a choice rather than a constraint. The branch sits *above* the per-session
  busy guard in `Session.command`: below it, a `/restart` typed into a busy
  session could never report which sessions are busy.
- **A WebUI toolbar button** beside `♻️ reload`, guarded by `confirm()` like
  `🔥 wipe`, because it disconnects everyone and not just this page. On a
  refusal carrying `busy` it offers a second confirm that resends with `force`.
- **No `POST /restart`.** The WS command reaches all three clients; an HTTP
  route would be a second way in with its own auth surface and no new reach.
- **No reconnect for `chat.py`.** A real one is 40–60 lines — the `ws` hoisted
  out of three closures, a second queue sentinel, `last_seq` tracking, and a
  guard on the unjoinable stdin thread. It keys its parting line on close code
  1012 instead, which is the honest size for the problem.
- **No new event type and no `PROTOCOL_VERSION` bump.** All three clients
  already render `notice`; the close code carries the rest.

## Also fixed here

`ssh_forward.Forward.close()` killed a timed-out forward without waiting for it.
Init reaped the orphan at exit, so it never mattered — until the process started
surviving its own restarts, at which point the new image has no `subprocess`
bookkeeping to collect anything and each restart would leave one more permanent
zombie. It now waits, bounded.

## What is not covered

The Discord bot is a sibling process started by `serve.sh`, not a child of the
core. `/restart` does not touch it; it just reconnects on its own backoff. So
someone who edits `discord_client.py` and types `/restart` has not run the code
they just wrote, and the reply and the broadcast notice both say so.
